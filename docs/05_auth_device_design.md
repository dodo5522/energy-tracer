# 認証・デバイス設計

最終更新日: 2026-11-15

この文書は個人利用を前提とした将来の設計方針であり、記載した認証・認可やロール分離は実装・検証済みを意味しない。全体構成は [アーキテクチャ設計](02_architecture.md)、実装の学習手順は [チュートリアル](tutorials/better-auth-postgresql.md) を参照する。

## ブラウザからの利用

1. ブラウザは TanStack Start の Better Auth API でログインし、セッション Cookie を受け取る。
2. 保護されたリクエストを受けた TanStack Start のサーバー側がセッションを検証する。
3. フロントエンドはクライアントから届いた本人情報用ヘッダーを除去し、検証結果のユーザー ID を Rust API に渡す。
4. Rust はユーザー ID と設備・データの所有関係を確認してから処理する。ブラウザが指定したユーザー ID は信用しない。

同一 ECS タスク内の Rust API は localhost のみで待ち受け、直接公開しない。これは同じタスク内の呼び出し元を信頼する設計であり、localhost 自体は呼び出し元認証を提供しない。フロントエンドのプロキシが任意パス・任意ヘッダーを転送しないこと、保護対象ルート・操作ごとにサーバー側でセッションと認可を確認することが前提。API を別タスクに移す、または信頼できない呼び出し元を追加する場合はサービス間認証を再設計する。画面での `useSession` やルートガードだけでは API を保護できない。

## デバイスと API キー

1 人のユーザーは複数デバイスを登録でき、各デバイスに API キーを発行する。Rust がデバイス・キーの発行、検証、失効を担当し、SeaORM で業務データを管理する。1 デバイスに複数キーを一時的に持たせることはローテーションの候補であり、制限は未確定。

- ログイン済みユーザーが設定画面から発行・失効を依頼し、Rust が本人と対象デバイスの所有関係を確認する。
- 平文キーは発行時のみ表示する。安全な乱数で発行し、サーバーには検証用のハッシュを保存する。キーのログ・URL・追跡情報への記録を避ける。
- デバイスは HTTPS の Authorization ヘッダーでキーを送る。TanStack Start は専用の投稿経路を Rust へ転送し、ブラウザ用セッションを要求しない。Rust はキーの有効性からデバイスと所有者を特定し、許可された設備への投稿のみ受け付ける。
- キーは投稿権限に限定し、発行日時、失効状態、必要に応じて最終使用日時を管理する。漏えい時に個別に失効できるようにする。

キーの形式・ハッシュアルゴリズム・照合方法、スコープ、ローテーション、レート制限、デバイスと設備の対応、プロキシ経路の保護は実装前に決める。

## PostgreSQL のロールとデータ

| ロール | 想定する用途 |
|---|---|
| `migrator` | CI 等から Better Auth と SeaORM のマイグレーションを別々に実行 |
| `auth_operator` | フロントエンドの Better Auth 実行時に `auth` スキーマの認証テーブルを読み書き |
| `operator` | Rust 実行時に業務スキーマの設備・設定・デバイス・キーを読み書き |
| `tester` | テスト DB 用。実際のテストスキーマと権限は別途設計 |

ローカル初期化スクリプトには `auth_operator` と `auth` スキーマが追加され、`migrator` は両マイグレーションを実行する方針。Better Auth の実行用 `auth.ts` とマイグレーション用 `auth-migration.ts` は別の接続ロールを使用する。ローカルの Compose / Dev Container は開発用であり、同一コンテナ内でマイグレーションとアプリを実行する構成を許容する。本番では実行時ロールに DDL 権限を与えず、マイグレーション用とアプリ実行用の認証情報・タスクを分ける。Better Auth のスキーマ・マイグレーションと SeaORM の業務スキーマ・マイグレーションは各ツールで管理する。

Better Auth の `auth.user` と業務側のユーザー設定・デバイスはユーザー ID で紐付け、PostgreSQL 内では外部キーに `ON DELETE CASCADE` を付ける方針。外部キー作成には参照先への `REFERENCES` 権限または所有権が必要だが、実行時の `operator` にその権限や `auth` の読み取り権限は不要。ユーザー削除時の連鎖削除は PostgreSQL 内のみで、DynamoDB の時系列データの削除・保持は別途設計する。将来認証 DB を分離する場合は外部キーを置き換える必要がある。

ローカル初期化スクリプトは `auth` スキーマ、`auth_operator` の DB `CONNECT`・スキーマ `USAGE` と `migrator` が今後作成するオブジェクトのデフォルト権限を設定する。既存オブジェクトには別途 GRANT が必要。必要なシーケンス・関数権限は生成スキーマを確認して決める。`search_path` とツールのバージョンを合わせ、実行時とマイグレーション時の接続先が同じ `auth` スキーマになることを検証する。Neon で同じ権限設計が可能かも確認する。

本番では CI や専用タスクでマイグレーションを実行し、成功を確認してからアプリを更新する構成を検討する。別設定間でスキーマに影響する Better Auth の認証方式・プラグインを一致させる。

## 未決事項

- 本人情報を渡す内部ヘッダーの仕様、ルートごとの認可、保護されない経路の排除とテスト。
- ユーザー登録の制限、メール確認・回復、セッション管理とログアウト。
- API キー・デバイス管理の具体的なテーブル、発行上限、失効、保管、監査、攻撃対策。
- DynamoDB と PostgreSQL 間の所有関係・ユーザー削除時の保持／削除および失敗時の再試行。
- データ送信の頻度制御、冪等性、既存 API からの移行と切り戻し。
